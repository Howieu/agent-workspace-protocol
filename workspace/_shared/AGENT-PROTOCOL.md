# 项目工作协议 v4（所有 agent harness 通用）

适用于 Claude Code、Codex、Cursor 及任何读取本文件的 agent。本协议优先于各工具自带的"默认输出目录"设置。

下文的 `<工作区>` 指放所有项目的根目录（例如 `~/agent-workspace`），本文件位于 `<工作区>/_shared/`。

## 0. 底线
1. 按项目组织，不按工具组织。任何地方都不建以工具命名的目录或文件（claude/、codex/、HANDOFF-codex.md 之类）。
2. 每个项目只有一份规则（AGENTS.md）和一份交接（.agent/HANDOFF.md），所有 agent 共同读写；功能要做成什么样，以 docs/specs/ 里的 spec 为准。
3. 一个事实只存在一个项目里。别的项目要用，写路径引用，不复制内容。
4. 代码项目的 main 分支只放验收过的东西；改代码都在分支上做（第 10 节）。
5. 随做随存：任何时候关掉对话都不丢进度（第 3 节）。

## 1. 开对话与路由
对话一律在 `<工作区>` 开。用户的开场白只有三种：

| 用户说 | agent 做 |
| --- | --- |
| "继续 <项目>" | 进入项目，按 HANDOFF 的"下一步"接着做 |
| "<项目>：<要什么>"（含"新项目：<名字>"） | 进入项目，按第 9 节第 1 条分流 |
| "收工" | 第 5 节 |

路由步骤：
1. 读 `<工作区>/README.md` 的项目索引。
2. 属于已有项目 → 进入那个项目目录，按第 2 节开局。
3. 新项目 → 在 `<工作区>/<项目名>/` 按第 6 节建骨架，`git init` 并首次提交，在 README 索引加一行，然后写第一份 spec。
4. 拿不准属于哪个项目 → 列出候选问用户，不猜，也不先放到临时位置。
5. 不把产出放在 `<工作区>` 根目录、工具名目录或系统临时目录里当作交付。

## 2. 开局
1. 读项目的 AGENTS.md、.agent/HANDOFF.md，再读 HANDOFF"当前目标"指向的 spec。不读 .agent/log/，不通读其他文件。
2. 看 HANDOFF 的"进行中的会话"表：
   - "最后更新"超过 2 小时的行视为已结束：删掉，并告诉用户删了哪行
   - 其余行要动的文件和你重叠 → 先问用户；不重叠 → 可以并行
3. 加一行自己的会话（工具 | 开始时间 | 最后更新 | spec 与任务 | 分支 | 会动哪些文件），立即写回。
4. HANDOFF 顶部的"项目负责人"是人，不是工具，任何会话都不改它。
5. 用不超过 5 句话向用户复述：现状、本次目标、第一步。

## 3. 干活期间（随做随存）
- 每完成一个子任务，立刻做完这四件事，再开始下一个：
  1. 在当前分支提交改动（第 10 节）
  2. 勾掉 spec 里对应的任务和验收项，一起提交
  3. **重写** HANDOFF 的"一句话现状"和"下一步"（不是往后追加），更新自己那行的"最后更新"，在主目录提交 HANDOFF
  4. 功能细节只写进 spec，不写进 HANDOFF
- 改交付物、做不可撤销的操作、开始新的子任务之前，重读 AGENTS.md 的"硬约束"和"用户立下的规则"。
- 用户说出长期规矩（"以后都……""不要……""记住……"）→ 立即追加到 AGENTS.md 的"用户立下的规则"，格式 `- [YYYY-MM-DD] <规则>`，告诉用户写了什么。只记用户明确说的。
- 新规则和旧规则冲突 → 问用户以哪条为准，改掉旧条目，不让两条并存。
- 上下文被压缩过、发现自己和规则矛盾、或被用户纠正同类错误两次 → 先按本节存好，再建议用户开新对话。

## 4. 写共享文件的方法（防止多个会话互相覆盖）
- 每次写 AGENTS.md 或 HANDOFF.md 前，**重新读一遍文件**，在最新内容上修改，不用记忆里的旧版本整体覆盖。
- 只改自己负责的部分：HANDOFF 里别的会话那一行、别的会话写的进度，不删不改（第 2 节的过期行除外）。
- AGENTS.md 只追加或修改条目，不整体重写。

## 5. 收工（可选）
随做随存之后，用户不说"收工"直接关对话也不丢进度。用户说"收工""写交接"，或上下文快满时，再做：
1. 确认第 3 节的四件事都已做完，没有未提交的改动。
2. 把 HANDOFF 复制到 .agent/log/<YYYY-MM-DD-HHMM>-<工具>-<主题>.md 归档。
3. 删掉会话表里自己那一行；核对"一句话现状"和最近的提交不矛盾；提交。
4. 回顾本次对话，把应该长期生效的内容（新命令、坑、约束）列给用户确认，确认的写进 AGENTS.md。
5. AGENTS.md 超过 150 行 → 提出把细节移到 docs/ 并留指针的方案，由用户决定。
6. 给用户一句新对话的开场白，例如"继续 <项目名>"。

## 6. 项目骨架
  AGENTS.md            规则：唯一真相源，按 _shared/templates/AGENTS.md
  CLAUDE.md            只有一行 @AGENTS.md（可加 Claude 专属的操作习惯，不放项目事实）
  .agent/HANDOFF.md    当前状态：唯一交接，按 _shared/templates/HANDOFF.md
  .agent/log/          旧交接归档，只追加，平时不读
  docs/specs/          功能规格，一个功能一个文件，按 _shared/templates/spec.md
  docs/decisions/      决策记录，一事一文件
  work/ deliverables/ sources/ tmp/（tmp/ 写进 .gitignore）
其他工具的专属规则文件（如 .cursor/rules）同样只写"读 AGENTS.md"。

## 7. 什么放哪
| 信息 | 放哪 |
| --- | --- |
| 长期有效的项目规则、命令、禁区 | 项目 AGENTS.md |
| 全局进度：哪些 spec 在做、在哪个分支、下一步、待用户拍板 | 项目 .agent/HANDOFF.md（只在 main） |
| 某个功能做成什么样、怎么验收、拆成哪些任务、做到哪一步 | 项目 docs/specs/ |
| 某个方向性决定及理由 | 项目 docs/decisions/ |
| 属于另一个项目的事实 | 那个项目里；这里只写 `../<项目>/<路径>` |
| 某个工具自身的用法习惯 | 该工具的全局配置，不进项目 |
| 跨项目通用的规矩 | 本文件 |

## 8. 始终遵守
- 没有证据的事实标"待确认"，不写成确定表述
- 不推送、不部署、不删除、不发送、不购买，除非用户在当次对话里明确要求
- 凭据不写进任何文件

## 9. 规格驱动开发（SDD）
spec 是所有 agent 共用的契约：换工具、换会话、并行干活，都从同一份 spec 出发，不靠聊天记录对齐。

1. **分流**：收到"<项目>：<要什么>"，先查 docs/specs/，判断属于哪种，**先告诉用户判断结果**再动手：

   | 情况 | 处理 |
   | --- | --- |
   | 属于一份还在做的 spec | 在那份 spec 加任务，回到它的分支做 |
   | 改已完成的功能，没超出原目标和范围（bug、文案、参数） | 开 fix/ 分支，在那份 spec 的变更记录记一笔，不新写 spec |
   | 改已完成的功能，改变了目标或范围 | 新写 spec，"相关"写明取代旧 spec 的哪部分；旧 spec 状态改"部分取代" |
   | 全新的能力，或新项目 | 新写 spec |

2. **怎么写**：复制 _shared/templates/spec.md 到 docs/specs/<YYYY-MM-DD>-<功能>.md，在 main 上提交草稿。验收项必须能核对（命令、测试、评测、或一步具体的手动操作）。没有证据的写"待确认"。
3. **确认**：状态"草稿"交给用户看；用户说"做吧"或明确确认后改成"已确认"，在变更记录记一笔，再开分支实现。
4. **实现**：在分支上按"任务"逐条做，每做完一条按第 3 节存档。多个 agent 并行时，各自在会话表写清认领的任务编号和分支，"会动的文件"不重叠。发现 spec 不对 → 先改 spec 并记进变更记录，再改代码；方向性的改动先问用户。
5. **完成**：每个验收项附上证据（命令输出、测试名、截图路径）后勾选；全部勾完，状态改"已完成"。spec 不删，被取代时状态改"已废弃"或"部分取代"并写明被哪份取代。
6. **HANDOFF 的关系**：HANDOFF 的"当前目标"只写 spec 路径、分支和剩下的任务编号，不复述 spec 内容。

## 10. 分支与合并
1. **哪些项目要分支**：有代码的项目，改代码一律开分支。只有文档、简历、报告的项目直接在 main 上改。
2. **命名**：新功能 `feat/<spec 文件名去掉日期>`，修复 `fix/<简述>`。
3. **worktree**：分支检出到独立的 worktree 文件夹，多个 agent 并行互不干扰。工具能自动建 worktree 会话时用工具的，不能时用 `git worktree add`，放在项目的 .worktrees/ 下（写进 .gitignore）。
4. **分支上改什么**：只改代码和本功能那一份 spec。HANDOFF 不在分支上改，一律改主目录（项目根目录）里那份，并在 main 上单独提交。
5. **合并条件**：测试通过、spec 验收项全部勾完并附证据、用户说"合并"。三条齐了才合并回 main，然后删分支和 worktree，更新 HANDOFF。
6. **推送与部署**：只在用户当次明确要求时做。
7. **代码在子仓库的项目**（例如项目里的 app/ 是独立仓库）：代码分支开在子仓库；spec 和 HANDOFF 在外层仓库。
